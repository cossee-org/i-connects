{% comment %} One of the Lead's two dialogs for a member's own dates, in the app's standard modal (the same shape as task_dates_modal.html): ``field`` "start_date" draws the start date dialog, "deadline" the due date dialog. Each edits its one date and that date's own zone; the member's other own date, and its zone, are left as they are. So a member can start on one clock and be due on another. It opens on its own window event — ``open-start-date`` or ``open-due-date`` — dispatched by Set custom start date / Change start date and Set custom due date / Change due date in the completion table's details row. The event's detail fills it in: member the assignee's ProjectMember id name their display name, for the title value their own date (YYYY-MM-DDTHH:MM, in its zone), or "" reason the reason given for this own date, if any hasOwn whether they have this own date, which offers Remove timezone the zone saved with this date: "" for "Same as task", or null when they have no own date of this kind — the picker then starts on the Lead's system timezone A date they have no own value for starts on the task's, as the same moment in the zone the dialog opens on (memberDateDialog in base.html). Picking another timezone leaves the date and time as they are: they are saved as that clock time in the new zone. A date sent back at the task's moment, or emptied, follows the task's. Saving posts to tasks:member_dates with ``field`` and swaps #task-status-block, which this dialog sits inside, so the swap closes it. A refusal (a start after the deadline) comes back as a 400 whose text is shown above the buttons. Remove posts the same form with action=clear, which removes this date alone.
